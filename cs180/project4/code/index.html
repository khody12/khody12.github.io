Using MLPs for 2D Images

Before I utilize MLPs for NeRF. I'll utilize a simpler MLP to understand the image data of a 2D image.

Here is an image of the architecture I used. I utilized 4 linear layers of width 256. Using 3 ReLU activation functions between layers and a final sigmoid to transform the 3 nodes outputted by the last layer into usable RGB values.

Additionally, I used MSE for the loss function, an Adam optimizer, and learning rate of 1e-2. To get my results, I ran for around 2500-3000 iterations with a batch size of 10k.

Hyperparameter Tuning: Frequency & Width

The performance changes massively if the frequency of either the width or the positional encoding is substantially changed.

Having a high positional encoding allows the model to learn much better as the input tensor is substantially larger. If shrinks, performance suffers.

Having a healthy layer width is also quite important and allows the model to understand higher frequencies. As seen here, higher frequencies get completely lost when frequency or width is too low.

Implementing a NeRF from Scratch

A NeRF works by shooting rays out of many images that are taking a picture of one object from different positions. Accordingly, the most important thing is having a way to sample rays.

1. Camera-to-World Coordinate Conversion

First, I worked to implement the camera-to-world coordinate conversion. This is the transformation between the world space $X_w = (x_w, y_w, z_w)$ and the camera space $X_c = (x_c, y_c, z_c)$.

This can be defined as a 3x3 rotation matrix and a translation vector. I take the camera-to-world matrix given by calibration, add ones to our coordinates, and matrix multiply.

Implementation

2. Pixel-to-Camera Conversion

Next, we need to implement pixel-to-camera conversion. The idea here is to take the intrinsic matrix of the camera ($K$) and matrix multiply the inverse of the intrinsic by our pixel coordinates which is then scaled by a depth factor which we set to 1.

Additionally, I add 0.5 to the pixel coordinates so that we're shooting rays from the center of the pixel rather than the top left.

$$ \begin{bmatrix} x_c \\ y_c \\ z_c \end{bmatrix} = K^{-1} \begin{bmatrix} u + 0.5 \\ v + 0.5 \\ 1 \end{bmatrix} \cdot z_{depth} $$

3. Pixel-to-Ray Conversion

Next, we need to implement pixel-to-ray so that we can see what direction a ray goes so that we can eventually sample points along that ray.

First we will retrieve the translation component from the camera-to-world matrix to obtain the origin of the ray ($r_o$). This is because the origin is just the location of the camera in world coordinates.

From here, we need to obtain the ray direction. So we choose a point along this ray where depth equals 1 and then find its coordinate $X_w$ in the world space.

$$ \vec{d} = \frac{X_w - r_o}{||X_w - r_o||_2} $$

I implemented this by simply taking the origin from slicing the c2w matrix. Then I used my previously implemented pixel_to_camera and camera_to_world functions to first translate the pixel to the camera space, then from camera space to world space.

Finally, I subtracted the ray origin from the world coordinate. Importantly, all of the above functions support batched coordinates by utilizing torch/numpy broadcasting so that we don't have to run for loops in the future.

Setting up the Dataloader & Sampling Rays

Now, we need to put it all together to build a functional dataloader that can sample rays and eventually feed it to our MLP model.

In order to sample rays, I decided to precompute all possible rays. So for each image, I compute the ray for each pixel. This is implemented by first creating a grid of (u,v) coordinates that matches the shape of the image.

Now that we have a dataloader, we need to be able to create samples along the ray. The key here is we need a start and stop place to sample.

In the classic lego dataset, the near is set to 2, far set to 6. So within this range we need to samples random points so that the model can learn the color and density of a particular point in space.

We use numpy to randomly find points between 2 and 6. We can visualize what this looks like using Viser:

MLP Architecture for NeRF

Finally, we have our model. This model is equipped with significantly more layers than our MLP model for 2D images.

To implement this, I used torch layers and positional encoding along the 3 dimensions of our world coordinate. I used a positional frequency of 10 for the coordinate position, and a positional frequency of 4 for the ray direction.

Positional encoding was implemented using sines and cosines as well as a range of multiples of 2 to let the model understand higher frequencies. Additionally, the 3D coordinate was concatenated halfway through the first set of linear layers to prevent the model from forgetting about the input (skip connection).

Volume Rendering Function

Now we have the most intriguing part of the NeRF project. The idea of assigning every point that we sample in space a certain density and color, then integrating along a ray to get the final color.

Each sample along the ray has a weight assigned to it based on the probability that a ray hits it first before hitting any other ray.

We will take the probability of a ray not terminating before a sample location, then multiply that by the probability of terminating at the sample location, finally it's scaled by the color obtained by the network.

$$ \hat{C}(\mathbf{r}) = \sum_{i=1}^N T_i (1 - \exp(-\sigma_i \delta_i)) \mathbf{c}_i $$ $$ \text{where } T_i = \exp\left(-\sum_{j=1}^{i-1} \sigma_j \delta_j\right) $$

This can be implemented by utilizing torch.cumprod and torch.sum.

Training the NeRF on the Lego Dataset

We can take a look at how the model will train on the classic lego dataset here from 0 to 1900 iterations.

It starts off as a fuzzy mess but slowly starts to sharpen up and by iteration 1900 or so begins to look pretty reasonable.

Additionally, I render a depth map of the lego dataset by passing in distances rather than colors to the volume rendering function. To remove random white noise, I use an accumulation mask. For a white pixel to render, it must have a certain level of confidence that it actually went through solid mass. This probability is represented by the weights, and the sum of the weights gives us the total probability that the ray passed through mass.

This prevents the renderer from finding one point where the model thinks density is high and then rendering that. These specks are often just random noise so having an accumulation tracker to see what the probability is of a ray hitting true mass is critical

Challenges & Analysis

This process was somewhat painstaking. I went through many iterations of calibration till I ended up with a result that had legible results.

One thing that is critical is during the NeRF process, you should really try to make sure the aruco tags end up in the corners of your shot so that they can capture more distortion. Second, taking lots of photos like a dome over the calibration introduces lots of error and is not helpful. All you need is many variations of 3 main angles, top down, about 45 degrees, and then really quite low, almost parallel to the paper.

Next, scenes that have a variety of different colors are important for debugging. I, in error, thought that trying a scene like a carpet with a very constant color and then an object on top of it would make the training process more smooth but I found that the model could find lots more local minimas where it just memorizes the average color within 100 iterations and gets quite high PSNR values (20+).

In the end, I decided on a smaller arc shape instead of a 360 dome and I increased training images from ~35 to ~70. This caused drastically increased performance despite PSNR values not being terribly high at around ~17 when trained for 5000 iterations.

With that said, in this approach, my validation PSNR value was quite close to my training PSNR. Most of the error came from a part of the image seeing far into the background while most of the image was focused on the desk.
