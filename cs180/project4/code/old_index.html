Using MLPs for 2D Images

Before I utilize MLPs for NeRF. I'll utilize a simpler MLP to understand the image data of a 2D image.

Here is an image of the architecture I used. I utilized 4 linear layers of width 256. Using 3 ReLU activation functions between layers and a final sigmoid to transform the 3 nodes outputted by the last layer into usable RGB values.

Additionally, I used MSE for the loss function, an Adam optimizer, and learning rate of 1e-2. To get my results, I ran for around 2500-3000 iterations with a batch size of 10k.

Implementing a NeRF from Scratch

A NeRF works by shooting rays out of many images that are taking a picture of one object from different positions.

Accordingly, the most important thing is having a way to sample rays.

First, I worked to implement the camera-to-world coordinate conversion. This is the transformation between the world space X_w = (x_w, y_w, z_w) and the camera space X_c = (x_c, y_c, z_c).

This can be defined as 3x3 rotation matrix and a translation vector like we see here.

Here, I basically just take the camera-to-world matrix that is given by calibration, add ones to our coordinates and matrix multiply.

Implementing a NeRF from Scratch

Next, we need to implement pixel-to-camera conversion.

The idea here is to take the intrinsic matrix of the camera and matrix multiply the inverse of the intrinsic by our pixel coordinates which is then scaled by a depth factor which we set to 1.

Additionally, I add 0.5 to the pixel coordinates so that we're shooting rays from the center of the pixel rather than the top left.

Implementing a NeRF from Scratch

Next, we need to implement pixel-to-ray so that we can see what direction a ray goes so that we can eventually sample points along that ray.

First we will retrieve the translation component from the camera-to-world matrix to obtain the origin of the ray. This is because the origin is just the location of the camera in world coordinates.

From here, we need to obtain the ray direction. So we choose a point along this ray where depth equals 1 and then find its coordinate X_w in the world space.

The normalized ray direction is then X_w - r_o / L2 norm of (X_w - r_o).

I implemented this by simply taking the origin from slicing the c2w matrix. Then I used my previously implemented pixel_to_camera and camera_to_world functions to first translate the pixel to the camera space, then from camera space to world space.

Finally, I subtracted the ray origin from the world coordinate.

Importantly, all of the above functions support batched coordinates by utilizing torch/numpy broadcasting so that we don't have to run for loops in the future.

Setting up the Dataloader

Now, we need to put it all together to build a functional dataloader that can sample rays and eventually feed it to our MLP model.

In order to sample rays, I decided to precompute all possible rays. So for each image, I compute the ray for each pixel.

This is implemented by first creating a grid of (u,v) coordinates that matches the shape of the image. This grid is repeated for each image that we have.

Similarly, we need to repeat the camera-to-world matrix for each of these pixels so that each ray can eventually be sampled for training.

I then call pixel_to_ray on this massive batch of pixels to create the full set of rays for my dataset.

Sampling Rays

Now that we have a dataloader, we need to be able to create samples along the ray. The key here is we need a start and stop place to sample.

In the classic lego dataset, the near is set to 2, far set to 6. So within this range we need to samples random points so that the model can learn the color and density of a particular point in space.

We use numpy to randomly find points between 2 and 6 and then add these random values to set buckets defined by the length of the space we're sampling divided by the number of samples along the ray we need.

This will give us the selected number of samples amount of points along the ray that we will use to train.

We can visualize what this looks like using viser.

MLP for NeRF

Finally, we have our model. This model is equipped with significantly more layers than our MLP model for 2D images.

To implement this, I used torch layers and positional encoding along the 3 dimensions of our world coordinate. I used a positional frequency of 10 for the coordinate position, and a positional frequency of 4 for the ray direction.

Positional encoding was implemented using sines and cosines as well as a range of multiples of 2 to let the model understand higher frequencies.

Additionally, the 3D coordinate was concatenated halfway through the first set of linear layers to prevent the model from forgetting about the input.

ReLU's are used for activations between layers and a final sigmoid is used for the ray direction to get an RGB value.

Volume Rendering Function

Now we have the most intriguing part of the NeRF project. The idea of assigning every point that we sample in space a certain density and color. Then integrating along a ray to get the final color and density.

Each sample along the ray has a weight assigned to it based on the probability that a ray hits it first before hitting any other ray.

We will take the probability of a ray not terminating before a sample location, then multiply that by the probability of terminating at the sample location, finally it's scaled by the color obtained by the network at the sample location.

Then I use torch.sum to get the total value of the transmittances multiplied by the probabilities which gives us the final color.

Calibrating my iPhone Camera with Aruco Tags and Creating a NeRF on my own dataset.

Now that I have created a NeRF of the classic Lego dataset. I'll move on to trying it on my own data.

Creating a NeRF with data captured on my phone in location around my apartment proved to be easier said than done. Aliasing on the many pieces of wood in the apartment made this tricky and I didn't trust the NeRF to deal with this so I laid pieces of paper down underneath my object to reduce error.

Once I calibrated my camera via Aruco tags. I needed to undistort the images that I captured of my object. The iPhone camera didn't have a lot on the wide angle lens, but there was still some minor editing needed to be done.

Here is the visualization of my rays in viser.

Training the NeRF model on my data

This process unfortunately did not go smoothly. While training PSNR steadily rose to more than 18, validation PSNR did not fare well. Validation PSNR peaked at around 13.5 at iteration 500-700 and gradually slipped to 12 as iterations went to 3000.

You can generally see the white paper that the object should be sitting on top of, but generally it is not super clear.

If I had to think of reasons why my results don't look great here. I think there might be some inaccuracy with the aruco tags I chose as across a few different calibration attempts, I often got different results.

My focal lengths stayed in around the same territory of 200's, but sometimes low 200 like 200, 201, sometimes up to 215. Distortion also jumped around quite a bit from really quite significant numbers, to relatively low numbers for the calibration images I landed on

The actual model and ray sampling should be quite reasonable as the lego dataset reached healthy PSNR values and the frustum visualization of my rays for my own data also looked reasonable, but certainly not as good as the lego dataset.

Looking at Renders During the Training Process.

During the training process, it starts out as a blur and does start to sharpen over time. But it doesn't really capture the details of the scene.

The table with white papers stacked on it does slowly start to come into view but the things around it, specifically in the background do not load in very well.

While tuning hyperparameters for this model, I noticed I needed to reduce the near point for sampling down significantly. The scale that the lego dataset was using was about 10x greater than mine so it needed to be adjusted down to about 0.1 which is what I ultimately went with.

I tried adjusting the far point to greater distances, but never could find a great sweet spot where the validation PSNR was able to actually track the training PSNR. With some more in depth tuning, I think it's possible that my data could work well but a potential issue is that the background might've been too much further away than the foreground.
